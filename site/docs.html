Documentation

Oracle Plan Visualizer

A client-side web application that turns Oracle execution plan output into an interactive, annotated picture. Paste DBMS_XPLAN, SQL Monitor (text or XML), JSON or xbi.sql output and get a plan tree with hotspots, cardinality analysis, advisor findings, a flame graph, a Sankey diagram, side-by-side plan comparison, and more.

Everything runs in your browser tab. There is no backend, no account, and nothing is uploaded. The hosted build on GitHub Pages is a static site, and you can serve the same static build yourself with Docker or any web server (see Installation).

Who it's for

DBAs, developers, consultants

Anyone who reads Oracle plans and would rather see the shape of the problem than scroll through ASCII pipes.

What you need

A plan and a browser

Any modern browser. For runtime statistics (A-Rows, A-Time) you need SQL Monitor output or DBMS_XPLAN with ALLSTATS.

Cost

Free, open source, MIT

Source on GitHub. Self-host it, fork it, embed it in your internal tooling.

Privacy

Plans stay local

Parsing, layout and analysis all happen client-side. Settings live in your browser's localStorage. See Privacy.

Getting started#

Thirty seconds from a plan in SQL*Plus to a picture. No install needed for the hosted app.

1. Open the app

Go to the hosted app (or your own deployment). The input drawer at the top is open on first load with an empty text area.

2. Load a plan

Three ways in:

  • Paste plan output into the text area and press Cmd+Enter (Ctrl+Enter on Windows/Linux) or click Visualize.
  • Drop a file (.txt, .xml, .json) onto the input area.
  • Load Example in the top bar opens a menu of bundled sample plans, grouped by format. Good for a first look; the Cardinality Trap (NL) example shows most analysis features at once.

The format is detected automatically (see Getting a plan out of Oracle for how to produce each one). If parsing fails, an error explains what was expected; see Troubleshooting.

3. Explore the tree

  • Click a node to open its details in the right panel: estimates, actuals, predicates, cardinality analysis, warnings, and attached metadata.
  • Arrow keys walk the tree: ↑ parent, ↓ first child, ←/→ siblings, Esc deselects.
  • Cmd/Ctrl-click several nodes for a multi-selection with aggregated statistics.
  • Hover an operation name for an expert description of what that Oracle operation does.
  • With nothing selected, the right panel shows a Hotspots summary and the Findings list. Click any entry to jump to that node.

4. Switch views

The view tabs in the top bar switch between Tree, Tabular, Sankey, Flame, Plan Text, SQL, and (depending on the loaded format) Metadata, Monitor and Experimental. Switching never re-parses the plan, so it is instant. Details in Views.

5. Find the problem

Hotspots, cardinality mismatches, spills to disk, and the advisor's findings are flagged automatically. See Analysis & findings for what each signal means.

Tip

Press Cmd+K at any time for the command palette. Every view, action, and appearance option is reachable from there by typing a few letters.

Installation & self-hosting#

You don't have to install anything to use the hosted app. Run it yourself when you want it on an internal network, want to pin a version, or want to enable the optional build-time features (database connector).

The app is a static single-page application: the build produces a dist/ directory of HTML, JS and CSS that any web server can serve.

Option A — Docker (recommended for self-hosting)

The repository ships a multi-stage Dockerfile (Node 20 build → nginx 1.27 runtime) and an nginx.conf with the SPA fallback already configured.

git clone https://github.com/davidbudac/ora-explain-plan-viz.git
cd ora-explain-plan-viz

docker build -t ora-explain-plan-viz .
docker run --rm -p 8080:80 ora-explain-plan-viz
# → http://localhost:8080

The same two steps are wrapped as npm scripts: npm run docker:build and npm run docker:run.

Build arguments

ArgumentDefaultPurpose
APP_BASE_PATH/Serve the app under a sub-path, e.g. /planviz/. Leading/trailing slashes are normalized.
VITE_ENABLE_DB_AGENTunsetSet to 1 to compile in the "Connect to database" panel for the local database connector.
VITE_ENABLE_HOSTEDunsetShows the hosted (oraplanviz cloud) AI provider option. Off in the public build; only relevant if you run that backend.
 
docker build \
  --build-arg APP_BASE_PATH=/planviz/ \
  --build-arg VITE_ENABLE_DB_AGENT=1 \
  -t ora-explain-plan-viz .

Option B — Docker Compose

A docker-compose.yml is included with two services:

ServicePortWhen it runs
app8080Always. The standard build.
app-with-agent8081Only with --profile agent. Same app built with VITE_ENABLE_DB_AGENT=1.
 
# standard build on http://localhost:8080
docker compose up --build

# additionally build the connector-enabled UI on http://localhost:8081
docker compose --profile agent up --build

# stop and remove (pass the profile too if you started it, otherwise app-with-agent is left running)
docker compose down
docker compose --profile agent down

Both containers restart automatically (restart: unless-stopped). Edit the ports mapping in the compose file to change the host port.

Note

The database connector itself is not composed as a shared service on purpose. It holds database credentials and binds to 127.0.0.1, so it is designed to run on each user's own machine. The agent profile only builds a UI that knows how to talk to it.

Option C — From source (development)

Requires Node.js 20.19+ or 22.12+ (Vite 7's supported range; Node 21 and older 20.x releases are refused) and npm.

git clone https://github.com/davidbudac/ora-explain-plan-viz.git
cd ora-explain-plan-viz
npm install
npm run dev          # Vite dev server with hot reload → http://localhost:5173

Useful scripts:

CommandWhat it does
npm run devDev server on port 5173 (set PORT to override).
npm run buildType-check and build the production bundle into dist/.
npm run previewServe the production build locally to check it.
npm run build:pagesBuild with APP_BASE_PATH=/ora-explain-plan-viz/ (the GitHub Pages layout).

Build-time flags are plain environment variables during the build, for example VITE_ENABLE_DB_AGENT=1 npm run dev. A commented .env.example is in the repo root.

Option D — Static hosting (any web server, S3, GitHub Pages…)

Run npm run build (with APP_BASE_PATH set if you serve from a sub-path) and publish the contents of dist/. Two things to get right:

  1. SPA fallback. Unknown paths must serve index.html. The bundled nginx config does this with try_files $uri $uri/ /index.html;. Shared-plan links carry the plan in the query string, so they resolve to the root page anyway, but the fallback keeps deep links robust.
  2. Cache headers. Files under dist/assets/ are content-hashed and safe to cache forever; index.html should not be cached aggressively.
# the nginx.conf shipped in the repo
server {
  listen 80;
  server_name _;

  root /usr/share/nginx/html;
  index index.html;

  location /assets/ {
    try_files $uri =404;
    expires 1y;
    add_header Cache-Control "public, immutable";
  }

  location / {
    try_files $uri $uri/ /index.html;
  }
}

The public deployment is built exactly this way by the .github/workflows/deploy.yml GitHub Actions workflow, which also stages this documentation site under /welcome/.

Self-hosting and the plan_to_url.sql script

If you generate share links from inside the database (see Sharing), edit the DEFINE base_url line near the top of scripts/plan_to_url.sql so links point at your deployment instead of the public one.

Getting a plan out of Oracle#

Five input formats are accepted and auto-detected. Which one to use depends on what you need and what you're licensed for.

FormatQuick commandRuntime statsPredicates
DBMS_XPLANDBMS_XPLAN.DISPLAY_CURSOR('&sql_id', NULL, 'ALLSTATS LAST')With hint / STATISTICS_LEVELYes
SQL Monitor (text)DBMS_SQL_MONITOR.REPORT_SQL_MONITOR(sql_id=>'…', type=>'TEXT')YesNo
SQL Monitor (XML)… type=>'XML', report_level=>'ALL'Yes, plus ASH activityYes
JSONJSON_ARRAYAGG over V$SQL_PLAN_STATISTICS_ALLOptionalYes
xbi.sql@xbi &sql_id (Tanel Poder's TPT toolkit)YesNo

DBMS_XPLAN

The standard plan output. From the cursor cache:

SELECT * FROM TABLE(DBMS_XPLAN.DISPLAY_CURSOR('&sql_id', NULL, 'ALLSTATS LAST'));

From AWR when the cursor has aged out, or from a plan table after EXPLAIN PLAN FOR:

SELECT * FROM TABLE(DBMS_XPLAN.DISPLAY_AWR('&sql_id', &plan_hash_value, NULL, 'ALL'));

EXPLAIN PLAN FOR <your statement>;
SELECT * FROM TABLE(DBMS_XPLAN.DISPLAY(NULL, NULL, 'ALL'));

ALLSTATS LAST includes A-Rows, Starts and Buffers only if the statement ran with STATISTICS_LEVEL=ALL or the /*+ GATHER_PLAN_STATISTICS */ hint. The "Note" section (dynamic sampling, adaptive plans, SQL profiles, baselines…) is parsed and shown as tags.

SQL Monitor (text and XML)

Available for monitored statements: anything that ran longer than 5 seconds, ran in parallel, or carried the /*+ MONITOR */ hint. Requires the Diagnostics and Tuning Pack license.

SELECT DBMS_SQL_MONITOR.REPORT_SQL_MONITOR(
  sql_id       => '&sql_id',
  type         => 'XML',          -- or 'TEXT'
  report_level => 'ALL'
) FROM dual;

XML is the recommended format. It is the only SQL Monitor output that includes access/filter predicates, and it also carries the full SQL text, bind values, per-operation first/last active times and bucketed ASH samples, which power the Monitor tab and the Experimental timeline views. On 11g use DBMS_SQLTUNE.REPORT_SQL_MONITOR with the same parameters.

Large XML reports get truncated in SQL*Plus unless you raise the limits and spool to a file:

SET LONG 10000000 LONGCHUNKSIZE 10000000 LINESIZE 32767 PAGESIZE 0 TRIMSPOOL ON
SPOOL /tmp/sql_monitor.xml
SELECT DBMS_SQL_MONITOR.REPORT_SQL_MONITOR(sql_id => '&sql_id', type => 'XML', report_level => 'ALL') FROM dual;
SPOOL OFF

JSON and xbi.sql

JSON input is an array of rows from V$SQL_PLAN_STATISTICS_ALL (as produced by xdd.sql, Datadog's explain tool, or your own JSON_ARRAYAGG query). xbi.sql input is the raw SQL*Plus output of Tanel Poder's eXplain Better script. The full query for the JSON export is in the repo's docs/input-formats.md.

Skip the copy/paste

Run @plan_to_url.sql <sql_id> in SQL*Plus and it prints a ready-to-click visualizer link with the plan already embedded. See Sharing & export.

Using the app

The workspace#

The layout is one top bar plus three collapsible regions around the visualization.

  • Top bar. Brand, SQL ID, Plan A/B tabs, view tabs, Load Example, and all actions (theme, share, export, baseline script, client report, shortcuts). At narrow widths the view labels degrade to icons and then an overflow menu; actions collapse into a menu.
  • Input drawer. The text area, the parsed plan's metadata (SQL ID, plan hash, A-Rows, A-Time), format and metadata-bundle chips, and the annotation import/export controls. Collapse it once the plan is loaded.
  • Filter panel (left). Search, operation-type filters, numeric ranges, predicate filters, cardinality-mismatch slider, and the legend. See Filtering.
  • Detail panel (right). Selected node details, or the Hotspots summary and Findings list when nothing is selected. Also hosts the annotation editor.

Both side panels collapse via the tabs on their inner seam into slim rails that show a live filter count; click the rail to reopen. Two further modes give the visualization more room:

  • Maximize (F) hides everything except a slim tabs-only bar.
  • Focus mode (Z, persisted) hides both side panels and replaces them with a floating search/filters/findings pill and a selection-driven inspector card. It composes with maximize.

On narrow windows the side panels automatically switch to an overlay layout so the canvas keeps a usable width.

Using the app

Views#

All views render the same parsed plan and respect the active filters and selection. Tabs that need data the loaded format doesn't carry (for example Monitor without an XML report) are hidden.

Tree

The default view: the plan as a real tree, laid out by a custom algorithm (Dagre as fallback) using React Flow. Each node card shows the operation, object name, and configurable badges (cost, rows, bytes, A-Rows, A-Time, starts, predicate and partition indicators, query-block badge). The hottest node gets a red ring. Pan with drag, zoom with the wheel; the minimap and fit-to-view controls are in the corner. Edges can be animated, and the selection's root-to-node path can be emphasized (both toggles in the customize menu).

Tabular

A sortable, resizable table with every parsed column. Column widths persist. The hottest node is highlighted, and clicking a row selects it in every other view.

Sankey

A D3 Sankey where band width encodes the volume flowing between operations. Toggle the metric between Rows (estimated), Cost, A-Rows and A-Time to see which step moves the most data or burns the most time.

Flame

The plan as a flame graph, bars sized by each operation's self value (the metric minus its children's). Metric toggle: Cost, A-Time, A-Rows. Click a bar to zoom into that subtree; click the root or press Esc to zoom out.

Plan Text

The raw input, kept verbatim, with the selected node's line highlighted. Handy for quoting in a ticket.

SQL

The full SQL statement with syntax highlighting and a copy button. Available when the input carries the SQL text (SQL Monitor XML, some JSON exports, metadata bundles).

Metadata

The Schema Metadata explorer: tables, indexes and columns referenced by the plan, with per-object detail and a bundle overview. It can pop out into its own window. See Schema metadata.

Monitor

SQL Monitor XML only. Activity breakdown (CPU / I/O wait / PL/SQL / other), execution summary, session and environment, SQL text, bind variables, resource consumption and optimizer environment sections, straight from the report.

Compare

Appears when two plans are loaded: the per-operation delta dashboard. See Comparing two plans.

Experimental

Five research views behind a segmented switcher (the last one used is remembered):

  • Timeline. A Gantt of when each operation was actually active (from per-op first/last active offsets), with ASH wait-class cells per time bucket. SQL Monitor XML only.
  • Scatter. E-Rows vs A-Rows on log-log axes. Points on the diagonal are well estimated; distance from it is the cardinality error.
  • Waterfall. Wasted work: rows read vs rows returned per node, so a full scan that reads a million rows to return ten stands out.
  • Morph. An animated icicle that morphs from the optimizer's estimated shape to the actual one.
  • Waits. Per-line wait-class composition from ASH samples.

Using the app

Analysis & findings#

The app derives a set of signals from the plan as soon as it's parsed. None of them require a database connection.

Hotspots

With runtime statistics present, the node with the highest self A-Time gets a red ring and a "Hotspot" badge. The Hotspots panel (shown when nothing is selected) lists the top 5 nodes by A-Time, by cost, and the worst cardinality mismatches. Hotspot detection can be toggled from the command palette.

Cardinality mismatch

For every node with both E-Rows and A-Rows, the ratio between them is computed (per start, so nested-loop inner sides are compared fairly). Badges are shown at 3× (warn) and 10× (bad), in either direction. The detail panel explains the ratio and, if a metadata bundle is attached, whether the relevant column lacks a histogram or the table's stats are stale.

Plan advisor

A heuristic rules engine surfaces findings per node (badge on the card, section in the detail panel) and as a ranked list in the Findings panel. Ten rules:

Cardinality mismatch

Large E-Rows / A-Rows divergence, with the likely cause when metadata is attached.

Implicit conversion

TO_NUMBER/INTERNAL_FUNCTION wrapped around a column in a predicate, defeating indexes.

Cartesian merge join

A MERGE JOIN CARTESIAN that is not trivially small.

Nested-loop volume

A nested loop whose inner side starts very many times.

Parallel signals

Parallel execution downgrades, skew, or serial sections in a parallel plan.

Partition pruning

Partitioned access that scans all partitions (Pstart/Pstop = 1..N or KEY without pruning).

Selective full scan

A full table scan that returns a tiny fraction of the rows it read.

Spill to disk

Sorts, hash joins or group-bys that used temp space.

Stats issues

Dynamic sampling, missing or stale statistics (from the Note section or a metadata bundle).

Unused index

An index on the filtered column exists in the metadata bundle but the plan does a full scan.

Each finding has a severity, an explanation, and an optional suggestion. Suggestion hints are off by default and can be enabled in the Findings panel.

Other signals

  • Spill-to-disk badge on any node with temp-space usage, with details in the node panel.
  • Plan-level signals in the input-drawer header: partition pruning present, parallelism, spills, adaptive plan, dynamic sampling, SQL profile/baseline in use.
  • Operation tooltips: around 55 Oracle operations have an expert description shown on hover and in the detail panel.
  • Multi-select aggregates: with several nodes selected, the detail panel sums cost, rows, time and starts across them.

Using the app

Filtering & search#

The filter panel narrows what is drawn in every view. Nodes that don't match are dimmed (tree) or hidden (table). The active filter count shows on the collapsed rail.

  • Search across operation, object name and predicates. Matches are highlighted inside node cards.
  • Operation type checkboxes by category (table access, index access, joins, sorts, aggregations, parallel, partition, …).
  • Cost threshold, and with runtime stats, A-Rows, A-Time and Starts ranges.
  • Predicates: only nodes with access predicates, filter predicates, or both.
  • Cardinality mismatch slider: show only nodes whose E/A ratio exceeds the threshold you set.

The Legend at the bottom of the panel explains the current color scheme and can be hidden.

Using the app

Comparing two plans#

Typical use: before and after an index, a hint, a statistics refresh, or a version upgrade.

  1. Load the first plan as usual.
  2. Click + next to the Plan A tab in the top bar to add Plan B, and load the second plan into it. Each plan tab keeps its own input, selection and error state.
  3. The Tree and Tabular tabs now render both plans side by side in dual panes, with an accent on the active plan. Use Split compare in the command palette to toggle this.
  4. Open the Compare tab for the delta dashboard.

How nodes are matched

A three-pass matcher lines up equivalent steps:

  1. Exact ID: same node ID with a similar operation.
  2. Heuristic: same operation + object signature, closest depth wins.
  3. Unmatched: leftovers from either side are listed as added or removed.

Deltas are computed across nine metrics: cost, rows, bytes, A-Rows, A-Time, self time, starts, temp space and memory. Each is flagged as an improvement or a regression, and the metric pills at the top of the dashboard choose which ones are shown.

Using the app

Annotations#

Annotations are a layer on top of the plan for your own notes. They are kept in memory for the session and travel with the plan when you export it or share it.

  • Notes. Select a node and type in the annotation editor in the detail panel. Notes are timestamped and shown as an overlay on the node card.
  • Highlights. Seven colors (red, orange, yellow, green, blue, purple, pink) drawn as a ring around the node. The highlight style (ring, fill, or both) is configurable.
  • Bulk highlight. Multi-select several nodes and apply one color to all of them.
  • Groups. Name a set of nodes, give the group a color and an optional note. Groups are listed in the detail panel.
  • Overlays toggle. Hide all annotation overlays without deleting them (command palette).

Save and load

Save annotated plan (input drawer or command palette) downloads a JSON file containing the raw plan and all annotations. Loading it back restores everything; the file carries the plan hash and SQL ID so it is validated against the plan it was made for. Clear all annotations wipes the layer.

Using the app

Sharing & export#

Share via URL

Share plan via URL compresses the raw plan (gzip, base64url) into the ?plan= query parameter and shows the link in a dialog. Whoever opens it gets the plan loaded in their own browser; nothing is stored anywhere. Attached annotations are included. Very large plans (big SQL Monitor XML reports) can exceed what browsers accept in a URL; the dialog warns when that happens, and a saved JSON or the raw file is the fallback.

Share links straight from the database

scripts/plan_to_url.sql builds the same link inside Oracle, so no plan text ever passes through a clipboard:

SQL> @plan_to_url.sql an05rsj1up1k5             -- cursor cache, child 0
SQL> @plan_to_url.sql an05rsj1up1k5 1           -- specific child cursor
SQL> @plan_to_url.sql an05rsj1up1k5 "" MONITOR  -- SQL Monitor TEXT report (Tuning Pack)

The script is read-only, 19c+, and works in session-private temporary LOBs. It defaults to the public deployment; change DEFINE base_url at the top for a self-hosted one. Full argument and privilege reference in scripts/README.md.

Export as PNG

Renders the current tree view to a PNG image (command palette or top-bar menu). Useful for slides and tickets.

Client report

A self-contained HTML document with the plan, your notes and all findings. See Client report.

Going deeper

Schema metadata#

A plan alone doesn't tell you whether the stats were stale, whether a column had a histogram, or which indexes existed. A metadata bundle is a JSON document with table, column and index statistics (plus partitioning, constraints, simplified DDL, optimizer environment, and any baselines, profiles, patches or directives affecting the SQL) for the objects a plan touches. Attach one and the app annotates the plan with it.

1. Gather the bundle

Use the generated script. Either click Gather script in the app (it pre-fills the SQL ID) or take scripts/gather_plan_metadata.sql from the repo and run it in SQL*Plus or SQLcl (Oracle 12.2+):

SQL> @gather_plan_metadata.sql <sql_id> [<plan_hash_value>] [<spool_file>]
SQL> @gather_plan_metadata.sql LIST "HR.EMPLOYEES,HR.DEPARTMENTS"

It writes bundle.json (or the spool file you name). It reads DBA_* views first and degrades to ALL_*; objects it couldn't read land in a coverage_warnings list instead of failing the run. The script is read-only against the data dictionary.

2. Attach it

Drop the JSON onto the input area or use Attach metadata in the input drawer. A chip shows the bundle is paired with the plan (the pairing checks the SQL ID and plan hash, and warns on a mismatch).

3. What changes

  • Nodes with metadata get an inline badge; extra badges flag stale stats, missing stats, and "cardinality mismatch on a column with no histogram".
  • The node detail panel shows table/index/column stats next to the predicates, with column formatting in predicate text.
  • The Metadata tab opens the explorer (sidebar of objects, detail pages for tables, indexes and columns, bundle overview with coverage warnings). It can be popped out into a separate window to sit next to the plan.
  • Advisor rules that need schema knowledge (unused index, stats issues) become active.

A sample bundle ships with the Cardinality Trap (NL) and Partition Range Iterator examples so you can see the effect without a database.

SQL Plan Baseline script#

Once you've found a good plan, you may want to pin it. Create SQL Plan Baseline script (top-bar menu or command palette) generates a ready-to-run SQL*Plus script that creates a baseline via DBMS_SPM for the loaded plan's SQL ID and plan hash value.

  • Source: cursor cache, AWR directly (19c+), or AWR via a temporary SQL Tuning Set (11.2+).
  • Options: FIXED and ENABLED flags.
  • The script includes a pre-check query, the load call, verification queries, and a management crib sheet (disable, drop, evolve).

Nothing runs from the browser: you copy or download the script and run it yourself with the appropriate privileges.

Client report#

For consultants handing results to a client. Export client report packages the plan, your annotations, and all derived analysis into one self-contained HTML file. Fill in title, client and prepared-by (the last two are remembered), write an executive summary, toggle sections, and check the live preview.

Sections available:

  • Header metadata, headline stat cards and optimizer-note tags
  • SQL statement
  • Full plan table with hotspot marker, highlight chips, inline notes and an estimate-quality column
  • Consultant notes, groups and highlights
  • Advisor findings with recommendations
  • Top self-time hotspots and worst cardinality mismatches
  • Predicates, execution environment and bind variables
  • Raw plan appendix

Download as .html or open the print view and save as PDF. Fully offline.

Database connector (optional)#

Instead of copying plans out of SQL*Plus, you can fetch them straight from a database with the oraplanviz-db-connector companion. It is a small Python program that runs on your own machine, connects to Oracle with python-oracledb in thin mode (no Instant Client), and exposes a localhost JSON API that the app's Connect to database panel talks to.

Privacy model

Credentials and plan text only ever flow between your browser and the connector on 127.0.0.1. The connector binds to localhost only, requires a random bearer token on every request, and only answers allow-listed origins. The hosted app never sees your database.

Setup

  1. Build the app with the panel enabled: VITE_ENABLE_DB_AGENT=1 npm run dev, or the Docker agent profile (port 8081). The public GitHub Pages build does not include it.
  2. Install and start the connector:
pipx install oraplanviz-agent

oraplanviz-agent \
  --allow-origin http://localhost:5173 \
  --dsn dbhost.example.com:1521/pdb1 \
  --user planviz            # password is prompted, never a CLI argument
  1. It prints its URL (default http://127.0.0.1:8521) and a bearer token. Paste both into the Connect panel in the input drawer (or open it from the command palette).
  2. Enter a SQL ID. The plan is fetched along with a metadata bundle when possible; if the metadata gather fails you still get the plan, with a notice.

Flags: --port, --host (keep it at 127.0.0.1), --allow-origin (repeatable), --token. Add your self-hosted app's origin to --allow-origin when not using the dev server.

AI analysis#

Coming soon

The AI entry points are present in the app but currently disabled and labelled "Coming soon" while the feature is finalized. The description below is what the feature does when enabled.

An optional LLM-assisted review of the loaded plan, or of a Plan A vs Plan B comparison. You pick a provider (Anthropic, any OpenAI-compatible endpoint, the local connector's agent, or a hosted account), enter a key, and click Run. The report streams into an AI tab as markdown, with findings linked back to plan nodes, and a follow-up chat lets you ask questions about it.

Appearance & density#

Three independent appearance axes, all persisted to localStorage and all reachable from the command palette.

AxisOptionsWhat it changes
ThemeLight, Dark (follows the OS by default)Everything.
App paletteSlate (default), Graphite, Teal, Violet, PaperNeutral surfaces and the accent color. Data colors are untouched.
Color schemeHigh Contrast, Semantic (default), Est ⇄ Act, Icon Rail, Ticker, Stripe, Tinted, TerminalHow plan data is painted on nodes. The last three restyle the node card itself (category spine, quiet tint, square mono "terminal" look).

Density presets

  • Minimal: operation, object, one mono metric line, and an amber dot for collapsed warnings. Hovering a node for a moment opens a card with the full Est/Act grid, badges and predicates.
  • Compact (default): badges and key metrics on the card.
  • Detailed: everything, including predicate text.

Node display options

The Customize view menu (and "Toggle …" palette commands) switch individual elements on the node cards: object name, Rows/E-Rows, Cost, Bytes, A-Rows, A-Time, Starts, predicate indicators and details, partition pruning, query-block badge and grouping, hotspot / spill / cardinality / advisor badges, metadata badges, edge animation, focus selection path, annotation overlays. Enable all and Disable all reset the lot.

Node indicator metric picks the single number shown on the badge in Minimal density: cost, A-Rows, A-Time, starts, or activity percent.

Privacy & data handling#

  • No backend. The app is static files. Parsing, layout, analysis, comparison and report generation all run in the browser tab. The public deployment makes no network requests with your data.
  • localStorage holds view preferences (theme, palette, color scheme, density, panel states, column widths, client/author names for reports). It never holds plans or keys.
  • Share URLs contain the plan itself, compressed. Treat a share link like the plan text: anyone with the link has the plan. Nothing is stored server-side.
  • Annotations are in memory only until you export them.
  • Database connector traffic stays on your machine (browser ↔ 127.0.0.1). Credentials are never sent to the app's host.
  • AI analysis (when enabled) sends the plan and optional metadata to the provider you chose, only when you click Run. Keys live in sessionStorage for the tab's lifetime.

Plans often contain object names and literal values from predicates. If that is sensitive, self-host the app on your own network; the behavior is identical.

Troubleshooting & FAQ#

"Could not detect the plan format"

The parser looks for the DBMS_XPLAN table header (| Id | Operation |), the SQL Monitor "SQL Plan Monitoring Details" header, an XML <report> root, a JSON array, or the xbi.sql header. Make sure the whole table is pasted including the header row and the dashed separator lines, and that line wrapping hasn't broken rows (set LINESIZE 300 or more in SQL*Plus).

The XML report is truncated or the tree is incomplete

SQL*Plus cuts long CLOB output at LONG. Use the spool recipe in Getting a plan out of Oracle with SET LONG 10000000.

No A-Rows / A-Time, only estimates

Your input has no runtime statistics. Use SQL Monitor output, or run the statement with /*+ GATHER_PLAN_STATISTICS */ (or STATISTICS_LEVEL=ALL) and then DISPLAY_CURSOR with ALLSTATS LAST. Hotspots, cardinality analysis, flame A-Time and the Experimental views need actuals.

No predicates in the detail panel

SQL Monitor text reports and xbi.sql output don't carry predicates. Use SQL Monitor XML, or DBMS_XPLAN for the same SQL ID.

The Monitor or Experimental tab is missing

They need a SQL Monitor XML report. The timeline additionally needs the report's activity detail, which is present with report_level => 'ALL'.

Share link doesn't open / "corrupt or truncated"

The URL was cut by a chat client or email. Send the link as plain text, or fall back to the saved-JSON export. Very large reports may not fit a URL at all.

Self-hosted app shows a blank page under a sub-path

Rebuild with APP_BASE_PATH=/your/path/ so asset URLs are prefixed correctly, and make sure the server falls back to index.html.

Large plans are slow

Switch to Minimal density, collapse the side panels, or use the Tabular view. Filters reduce what's drawn in every view.

Do I need the Tuning Pack?

Only for SQL Monitor output and the MONITOR source of plan_to_url.sql. DBMS_XPLAN, JSON from V$SQL_PLAN_STATISTICS_ALL and xbi.sql need no extra license.

Contributing#

Issues and pull requests are welcome on GitHub.

  • Stack: React 18 + TypeScript (strict), Vite, React Flow, D3-sankey, Tailwind CSS.
  • Tests: Vitest with jsdom. npx vitest run --environment jsdom. Parser tests live next to the parsers in __tests__ directories.
  • Adding an example plan: drop a file named NN-category-Display Name.txt into src/examples/ (category dbms_xplan, sql_monitor, json or xbi). It appears in the Load Example menu with no code change. An optional .meta.json sidecar attaches a metadata bundle.
  • Plan that doesn't parse? Open an issue with the (sanitized) plan text and the Oracle version. Real-world plan shapes are the most useful contribution.
  • AI eval harness: evals/ backtests the test-case builder and analysis quality against your own Oracle scratch schema. See evals/README.md and its safety notes before running it.

The project's CLAUDE.md in the repo root doubles as an architecture overview of every module.
